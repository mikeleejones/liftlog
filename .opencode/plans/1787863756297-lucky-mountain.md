# AI Program Builder — replace JSON import with in-app chat program design

## Context

v0.6 (React/FastAPI-JSON-API migration) is complete and live in production
(see `CHANGES.log` entries 1-39). This is the next feature increment.

Today, creating/editing a multi-exercise program only works one way: the user
composes JSON in a separate `claude.ai` conversation, pastes it into a
textarea on the Profile tab, previews, and applies
(`frontend/src/pages/ProfilePage.tsx`'s `import` Section, backed by
`app/importer.py` + `POST /api/routines/import/{preview,apply}`). This is
clunky on a phone and requires leaving the app entirely.

**Decision (user-approved this session):** replace this JSON-paste flow with
a multi-turn AI chat, built into the Workout tab, that reuses the existing
Haiku integration pattern (`app/ai.py`) and the existing import engine
(`app/importer.py`'s `normalize`/`validate`/`plan`/`apply_import`) as the
underlying write path. The chat produces the *same* v2 program JSON shape
internally — nothing about the program/routine/exercise schema changes, only
how that JSON gets authored (AI conversation in-app instead of hand-paste).

User's explicit choices for this feature:
1. **Amend `CLAUDE.md`** — add a new decision entry superseding "Routines are
   designed with Claude in claude.ai and imported as JSON" and the working
   agreement "Routine design/programming questions are NOT Claude Code's
   job." (That agreement was about the coding agent's own scope during
   development — it does not block building an AI *product feature*, but the
   product-definition sentence does need to change since it's now literally
   false.)
2. **Reuse Claude Haiku** (same model/cost profile as substitution
   suggestions, same shared 100/day `ai_call_log` guardrail).
3. **Multi-turn chat refinement** (not a single-shot generate-and-preview).
4. **Replace JSON import entirely** — remove the Profile paste-JSON UI and
   its dedicated HTML/JSON endpoints. `app/importer.py` itself is *kept* as
   the internal write engine (reused by the new apply endpoint), just no
   longer exposed as a raw-paste feature. Tradeoff to flag: this removes the
   ability to hand-paste a `GET /export/program` backup back in — today
   there is no other restore path for that export either way (confirmed: the
   full-backup export already has no restore path at all, so this doesn't
   regress an existing working capability, it just closes a path that
   existed for a narrower one). Both export endpoints (`GET /export`,
   `GET /export/program`) are untouched — still available as downloads.

## Data model change

New table `program_draft` — a **singleton row** (id=1, same pattern as
`program_state`), holding the one in-progress AI conversation. Single-user
app, no need for draft history:

```
program_draft
  id            INTEGER PK (always 1)
  messages_json TEXT NOT NULL   -- JSON array of {role: 'user'|'assistant', content: string}
  program_json  TEXT            -- nullable; latest AI-proposed v2 program object, or NULL
  updated_at    TEXT NOT NULL
```

- `app/models.py`: add `ProgramDraft` model.
- New Alembic migration (`alembic revision --autogenerate` then hand-check,
  matching the pattern of the `20260827_01` baseline).
- `docs/schema.md`: add this as the 9th table, documented like the others
  (columns, purpose, lifecycle: created on first message, cleared on
  apply/discard).

## Backend: `app/ai_program.py` (new module, mirrors `app/ai.py`)

- `MODEL = ai.MODEL` (reuse the Haiku constant, don't duplicate the string).
- `_build_prompt(messages, exercise_names, active_program_context)`: full
  chat transcript + instructions to output the v2 program envelope shape
  (`{name, weeks, routines:[{name, week, exercises:[...]}]}`) using the exact
  field names/enums `app/importer.py` already validates
  (`MOVEMENT_PATTERNS`, `MUSCLE_GROUPS`, `EXERCISE_TYPES`, `DISPLAY_UNITS`) —
  this is what lets the response feed directly into
  `importer.normalize()`/`validate()`/`plan()` with zero translation layer.
  Prompt includes the user's existing exercise library names so the model
  prefers reusing an existing name (case-insensitive exact match is how
  `importer._upsert_exercise` decides create-vs-reuse) instead of minting
  near-duplicates.
- Response schema (`output_config: json_schema`, same technique as
  `_RESPONSE_SCHEMA` in `ai.py`): top-level object with
  - `message` (string) — the conversational reply shown in the chat bubble.
  - `ready` (boolean) — true once the model has enough info to propose a
    full program.
  - `program` (object, same shape as the v2 envelope `routines` field) —
    always structurally present (empty `routines: []` when `ready` is
    false) so the schema stays a single fixed shape, no `anyOf`/nullable
    complexity.
- `_validate_program(raw)`: delegate straight to
  `importer.validate({"version": 2, "program": raw})` — do not reimplement
  field validation. If it fails, treat as `ready = False` server-side
  regardless of what the model claimed (fail closed, matching `ai.py`'s
  existing philosophy) and drop the broken plan rather than showing it.
- `AICallError`/`AIValidationError` reused/imported from `ai.py` (or a tiny
  local subclass) so callers handle both modules' AI failures uniformly.

## Backend: new endpoints in `app/main.py`

Route group `/api/programs/builder/*`:

- `GET /api/programs/builder` — returns the current draft (`messages`, and
  `plan` recomputed via `importer.plan()` from `program_json` if present and
  still valid), or an empty draft shape if none exists yet. Used to resume
  on page load/tab switch.
- `POST /api/programs/builder/message` — body `{"content": "..."}`. Loads or
  creates the singleton draft, appends the user message, guards with
  `can_make_ai_call` (shared counter — returns `{"state": "limit", ...}`
  exactly like the substitution endpoint if exceeded), logs the call attempt
  *before* calling (same reasoning as the existing endpoint: a stuck retry
  still counts), calls `ai_program.generate_turn(...)`, appends the assistant
  message, persists `program_json` when `ready`, and returns
  `{"state": "ok", "message": "...", "plan": {...} | null}` — `plan` is the
  `importer.plan()` output (identical shape the frontend's existing
  `ImportPreview` component already knows how to render) or `null` if the
  model isn't ready yet or its `program` failed validation. On
  `AICallError`/`AIValidationError`, return `{"state": "error", "message":
  "couldn't reach the AI, try again"}` without mutating the transcript.
- `POST /api/programs/builder/apply` — re-validates the stored
  `program_json` (defense in depth — never trust a stale client), calls
  `importer.apply_import()` + commit (same as the old
  `POST /api/routines/import/apply` did), clears the draft, returns
  `{"result": {...}}` (same shape the frontend already expects from the old
  apply endpoint, so the post-apply query-invalidation/navigate logic in the
  frontend is unchanged).
- `POST /api/programs/builder/discard` — clears the singleton draft (used by
  a "start over" action and automatically after a successful apply).

Remove (per "replace entirely"): `POST /routines/import/preview`,
`POST /routines/import/apply` (HTML, `app/main.py` current lines ~1081-1112,
these are already-dead now that the SPA is the only served frontend — verify
no remaining reference before deleting), `POST /api/routines/import/preview`,
`POST /api/routines/import/apply` (JSON, current lines ~1119-1151), and the
`_parse_import` helper if nothing else uses it. Keep `app/importer.py`
unchanged — it's the reused write engine.
