## 5. `/api/latest-workout` bearer-token resolution

Current: `latest_workout` 1653–1694 calls `token_or_cookie_authed(request, db)` (326–341), which returns a **bool** — it looks up `SELECT id FROM api_token WHERE token = ?` (336), bumps `last_used_at` (339), and discards the owner.

Required change: the helper must return the **user row**, not a bool.

```
def token_or_session_user(request, db) -> Row | None:
    user = current_user_from_session(request, db)     # cookie path
    if user is not None:
        return user
    token = auth.bearer_token(request)                 # app/auth.py:25 — keep this
    if not token:
        return None
    row = db.execute(
        "SELECT u.* , t.id AS token_id FROM api_token t "
        "JOIN user u ON u.id = t.user_id WHERE t.token = ?", (token,)
    ).fetchone()
    if row is None:
        return None
    db.execute("UPDATE api_token SET last_used_at = ? WHERE id = ?", (utcnow(), row["token_id"]))
    db.commit()
    return row
```

- 1659 `if not token_or_cookie_authed(...)` → `user = token_or_session_user(...); if user is None: 401`

### 6.5 Assessment — you asked me to say so plainly

**The split is right for `display_unit` and `progress_reset_at`, questionable for `increment_kg`, and wrong for `is_archived`.**

- `display_unit` — unambiguously per-user. On a shared row, Alice toggling to lbs silently changes Bob's Active Workout screen. `POST /api/exercise/{id}/unit` becomes a cross-tenant write. **Must move.**
- `progress_reset_at` — unambiguously per-user. It is a marker on *one lifter's* training history; sharing it means Alice's reset wipes Bob's stall detection. **Must move.**
- `increment_kg` — genuinely ambiguous. It is partly a catalog property (a barbell goes up in 2.5 kg) and partly a user's equipment (micro-plates). But it is written by the **importer** (from program JSON) and the **seed**, i.e. from program data rather than user preference, and it is read by `progression.py` on the *same row* as `display_unit` in `_suggest_weight_reps` (98 and 101 are adjacent lines). Splitting one and not the other creates two resolution paths for one function. **Move it, for consistency, not because the semantics demand it** — and accept that `importer._upsert_exercise` now writes to two tables.
- `is_archived` — **do not move it. It is dead.** No code writes it. Putting it in `user_exercise_pref` builds per-user machinery for a feature that has never been implemented, and adds a COALESCE to the four hot read paths (`_exercise_list` 1192/1198 runs on every exercise-library keystroke) to resolve a column that is always 0. Leave it on `exercise` as a catalog-level flag. If per-user exercise hiding is later wanted, add it then, as a real feature with a route.

**Net recommendation: `user_exercise_pref(user_id, exercise_id, display_unit, increment_kg, progress_reset_at)` — three columns, not four.**

### 6.6 The real risk is not the split, it is the 15 rewritten queries

Every site in §6.1–6.3 reaches these columns through `SELECT * FROM exercise`, `SELECT e.*`, or an explicit `e.display_unit`. A missed site does not error — it silently returns the shared default, producing wrong units on a summary screen or wrong progression suggestions. That is the failure mode to engineer against.

**Concrete mitigation: one canonical resolved-exercise SQL fragment, used everywhere; zero bare `FROM exercise` outside it.**

Add to `app/db.py`:
```
EXERCISE_COLUMNS = """
  e.id, e.user_id, e.name, e.cue, e.youtube_query, e.movement_pattern,
  e.muscle_group, e.exercise_type, e.equipment, e.is_archived, e.created_at,
  COALESCE(p.display_unit, e.display_unit)   AS display_unit,
  COALESCE(p.increment_kg, e.increment_kg)   AS increment_kg,
  p.progress_reset_at                        AS progress_reset_at
"""
EXERCISE_FROM = ("FROM exercise e "
                 "LEFT JOIN user_exercise_pref p "
                 "  ON p.exercise_id = e.id AND p.user_id = :me")
EXERCISE_VISIBLE = "(e.user_id IS NULL OR e.user_id = :me)"
```
Note `progress_reset_at` is **not** COALESCEd — the shared column is dropped from `exercise` entirely (it has no meaningful catalog default), so it reads straight off the pref row and is NULL when absent, which is exactly the "scan all history" semantics `recent_sessions` already implements at progression.py:57.

**Parameter-style hazard:** `DatabaseSession.execute` (db.py:102–104) forwards to `exec_driver_sql` with `?` placeholders and **positional tuples**. Splicing a fragment containing its own placeholder into the middle of an existing query shifts every subsequent parameter index — a silent, catastrophic class of bug across ~15 rewritten statements. `exec_driver_sql` on pysqlite accepts a **dict with `:name` placeholders**, and `DatabaseSession.execute`'s signature already declares `Sequence | dict`. **Convert every query touching `EXERCISE_FROM` to named parameters** and never mix the two styles in one statement.

**Guard test:** add a test that greps `app/*.py` for `FROM exercise` / `JOIN exercise` and asserts every occurrence is either inside the `db.EXERCISE_*` constants or on an allow-list. Cheap, and it is the only thing that will catch a future contributor re-introducing a bare join.

**Write paths become upserts:**
```
INSERT INTO user_exercise_pref (user_id, exercise_id, display_unit)
VALUES (:me, :ex, :unit)
ON CONFLICT(user_id, exercise_id) DO UPDATE SET display_unit = excluded.display_unit
```
Affects `set_unit` (2232), `api_reset_exercise_progress` (1371), `importer._upsert_exercise` (325/333/340 — the `increment_kg` and conditional `display_unit` writes), `db._seed` (193), `_ai_exercise` (2133).

**Backfill:** the existing single user's current `exercise.display_unit`/`increment_kg`/`progress_reset_at` values must be copied into `user_exercise_pref` for that user for every exercise row where they differ from the column default, *before* the shared columns are repurposed as defaults. Otherwise the existing user silently loses every unit toggle and progress reset they ever made.

## 7. Uniqueness constraints

### 7.1 `exercise.name TEXT NOT NULL UNIQUE COLLATE NOCASE`
(`alembic/versions/20260827_01_baseline.py`, exercise DDL; `app/models.py:31`)

**Code paths that depend on global name uniqueness:**
| Site | What it does |
|---|---|
| `app/importer.py:187–189` (`plan`) | `SELECT id FROM exercise WHERE name = ? COLLATE NOCASE` → decides `"update"` vs `"create"` in the preview |
| `app/importer.py:316–318` (`_upsert_exercise`) | Same lookup → the actual find-or-create |
| `app/main.py:2123–2125` (`_ai_exercise`) | `SELECT * FROM exercise WHERE name = ? COLLATE NOCASE` → dedupes AI-suggested exercises |
| `app/db.py:191–196` (`_seed`) | Bare `INSERT INTO exercise` — relies on the table being empty |
| `app/main.py:1102` (`_builder_context`) | `ORDER BY name COLLATE NOCASE` — collation only, no uniqueness dependency |
| `app/main.py:1191–1199` (`_exercise_list`) | `name LIKE ?` + `ORDER BY name COLLATE NOCASE` — no uniqueness dependency |

There are **no `INSERT OR IGNORE` / `INSERT OR REPLACE` / `ON CONFLICT` statements anywhere in `app/`** today (grep confirms). Every dedupe is an explicit SELECT-then-INSERT.

**What must change.** SQLite treats NULLs as distinct in unique indexes, so a naive `UNIQUE(user_id, name)` permits unlimited duplicate *shared* rows. Two indexes are required:

```
-- shared catalog: at most one shared exercise per name
CREATE UNIQUE INDEX idx_exercise_shared_name
  ON exercise(name) WHERE user_id IS NULL;
-- private: at most one per user per name
CREATE UNIQUE INDEX idx_exercise_user_name
  ON exercise(user_id, name) WHERE user_id IS NOT NULL;
```
Both rely on the column's `COLLATE NOCASE`, which is declared on the column so the index inherits it. Verify this after the table rebuild — if the rebuilt DDL loses `COLLATE NOCASE` on the column, the indexes become case-sensitive and the dedupe silently stops working. Add `COLLATE NOCASE` explicitly in the index definitions to be safe.

Note this permits a shared "Barbell Bench Press" **and** Alice's private "Barbell Bench Press" to coexist. That is the intended shared-vs-private model, but every lookup must then be deterministic about which one wins.

**Rewrite each dependent lookup to prefer the user's own row over the shared one:**
```
SELECT * FROM exercise
 WHERE name = :name COLLATE NOCASE
   AND (user_id IS NULL OR user_id = :me)
 ORDER BY user_id IS NULL       -- 0 (mine) before 1 (shared)
 LIMIT 1
```
Apply at `importer.py:187`, `importer.py:316`, `main.py:2123`.

**Decision required — where do newly created exercises land?** `importer._upsert_exercise` (338–344) and `_ai_exercise` (2130–2137) both create exercises. Recommendation: **created as private (`user_id = :me`)**. Shared rows stay a curated catalog seeded only by migration/`_seed`. Consequence: `_upsert_exercise`'s update branch (319–337) must **refuse to UPDATE a shared row** — today it rewrites `cue`, `youtube_query`, `movement_pattern`, `muscle_group`, `exercise_type`, `equipment`, `increment_kg`, `display_unit` in place. If Alice imports a program mentioning "Barbell Bench Press", she must not be able to rewrite the shared catalog entry for everyone. The branch becomes:
- matched row is **mine** → UPDATE as today
- matched row is **shared** → either (a) leave it alone and just reference it, or (b) fork a private copy. **Recommend (a)**: reference the shared row, write only the per-user bits (`display_unit`, `increment_kg`) into `user_exercise_pref`. This keeps the catalog stable and is exactly what the pref table is for.

**`db._seed` (191–196)** must become `ON CONFLICT DO NOTHING` + SELECT against the shared index (see §4) — otherwise the second user's bootstrap crashes.

## 9. Risks, and safest sequencing

### 9.1 `PRAGMA foreign_keys = ON` × Alembic batch rebuilds
`app/db.py:36–39` registers a `connect` listener on the module-level `engine` (33). Two important facts:

- `alembic/env.py:41–45` builds a **separate** engine via `engine_from_config` from `alembic.ini`. It imports only `app.config` (L8) and `app.models` (L9), neither of which imports `app.db`. **So Alembic currently runs with FKs OFF, and batch rebuilds are safe today.**
- `alembic/env.py:34,50` sets `render_as_batch=True`, and `include_object` (19–25) **excludes FK constraints from autogenerate** because SQLite reflection loses FK action metadata — meaning autogenerate will *not* reproduce `ON DELETE CASCADE` / `ON DELETE SET NULL`.

**Risks:**
1. If anyone adds `from app.db import …` to `env.py`, the listener fires on Alembic's connection too, and batch rebuilds start failing or silently repointing child FK references at `_alembic_tmp_*` tables. **Add a comment in `env.py` forbidding it**, and note that `PRAGMA foreign_keys` is a no-op inside a transaction, so you cannot simply turn it off in a migration body.
2. Autogenerate cannot be trusted for this migration. `routine_exercise.routine_id ON DELETE CASCADE`, `workout.routine_id ON DELETE SET NULL`, `set_log.workout_id ON DELETE CASCADE`, `substitution.workout_id ON DELETE CASCADE` (baseline DDL lines 68, 80, 89, 107) will be silently dropped by a batch rebuild driven by `include_object`.

**Recommendation: do not use `batch_alter_table` for this migration.** Write it in the same raw-SQL style the baseline already uses (`op.execute("CREATE TABLE …")`), doing a full ordered rebuild:
```
CREATE TABLE user / webauthn_credential / session / invite / magic_link
CREATE TABLE exercise_new (… user_id INTEGER REFERENCES user(id) ON DELETE CASCADE …)
INSERT INTO exercise_new SELECT …, NULL FROM exercise      -- all existing rows become shared
DROP TABLE exercise; ALTER TABLE exercise_new RENAME TO exercise;  -- then recreate indexes
… same for program, routine, routine_exercise, workout, set_log, substitution,
  program_state, program_draft, ai_suggestion_cache, ai_call_log, api_token
CREATE TABLE user_exercise_pref
INSERT INTO user_exercise_pref SELECT <admin>, id, display_unit, increment_kg, progress_reset_at FROM exercise
```
The database is 94 KB with one user. A full rebuild is trivially fast and gives complete control over FK actions, CHECK constraints, collations, and index recreation. Order matters: parents before children, and `DROP TABLE` of a parent while `PRAGMA foreign_keys` is OFF (Alembic's default) is safe.

**Do not forget to recreate `idx_setlog_exercise` and `idx_setlog_workout`** (baseline lines 101–102) — `DROP TABLE` takes its indexes with it.

### 9.2 `ALEMBIC_BASELINE` is an exact-equality assertion
`app/db.py:24` `ALEMBIC_BASELINE = "20260828_02"`, asserted at 153–157 (`version["version_num"] != ALEMBIC_BASELINE` → `RuntimeError`). Every new migration requires editing this constant in the same commit, or **the app refuses to start after `alembic upgrade head`**. This will bite at least twice during this work.

**Fix it once, at the start:** replace the constant with the actual head read from Alembic's own script directory:
```
from alembic.config import Config
from alembic.script import ScriptDirectory
def _expected_revision() -> str:
    return ScriptDirectory.from_config(Config(str(ROOT / "alembic.ini"))).get_current_head()
```
Then the check becomes "is the DB at head", which is what the error message at 155 already claims it means.

### 9.3 SQLite-specific migration constraints
- **Cannot** `ALTER TABLE … ADD COLUMN user_id INTEGER NOT NULL REFERENCES user(id)` — SQLite rejects adding a NOT NULL column without a default, and rejects a default on a column with a `REFERENCES` clause. Full rebuild avoids this entirely.
- `CHECK (id = 1)` on `program_state` (baseline) and `program_draft` (`20260828_02_program_draft.py:24`) can only be removed by rebuild.
- Partial unique indexes (`WHERE user_id IS NULL`) require SQLite ≥ 3.8.0 — universally available, but note `ON CONFLICT` **cannot target a partial index** in older SQLite. Verify `INSERT … ON CONFLICT(name) DO NOTHING` resolves against `idx_exercise_shared_name` on the deployed SQLite version, or fall back to explicit SELECT-then-INSERT in `_seed`.
- `COLLATE NOCASE` must be re-declared on the rebuilt `exercise.name` column *and* stated explicitly in both new unique indexes.

### 9.4 Runtime FK enforcement changes behaviour
With `PRAGMA foreign_keys = ON` at runtime (db.py:39), `ON DELETE CASCADE` on `user_id` means deleting a user wipes their programs, routines, workouts, sets, tokens, sessions, prefs. That is almost certainly what you want, but it is a footgun in tests and in any future admin UI. Decide explicitly per table and write it into `docs/schema.md`. Also: `exercise.user_id` with `ON DELETE CASCADE` deletes a user's private exercises — but `set_log.exercise_id` and `routine_exercise.exercise_id` reference `exercise(id)` with **no** ON DELETE action (baseline lines 69, 90, 108, 109), so that cascade will be **blocked** by a FK violation if the user has ever logged a set against a private exercise. Either use `ON DELETE RESTRICT` on `exercise.user_id` and require explicit cleanup, or add `ON DELETE CASCADE` down that chain. **This will fail the first time you try to delete a real user.**

### 9.5 One engine, created at import time
`app/db.py:33` builds the engine at module import from `DB_PATH`. `tests/conftest.py:1–15` documents this as the reason for one shared test DB. It also means **there is no per-request DB session dependency** — every handler calls `get_db()` / `db.close()` by hand (60+ sites). The new auth dependency needs a `db` too. Recommend a single FastAPI dependency that yields `(db, user)` and closes the session, replacing the manual `get_db()`/`db.close()` pairs in the handlers you are already editing — but **do not** attempt to convert all 60 in one pass.
